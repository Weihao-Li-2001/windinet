─────────────────────────────────────────────────────────── Answers, for the proposal form ───────────────────────────────────────────────────────────
Average number of processes. One MPI/DDP rank per GPU or XPU tile, plus 4 dataloader worker processes per rank. Production jobs run 2-8 ranks on a 
single node (10-40 OS processes); the average across the 4 job types in use is 5.5 ranks / 23.5 processes, and the largest configuration is 8 ranks / 
40 processes. Multi-node is supported by the launchers but not yet in production use.

Average job memory (total over all nodes). Both stages run on a single node. VAE finetuning at 8 ranks: ~66 GB host RAM and ~181 GB device memory, 
scaled from a measured 2-rank run (16.41 GB host, 45.19 GB device). DiT training at the same width: ~159 GB host and ~380 GB device. Smaller 2-GPU 
jobs -- the lrz_ai default -- are what was measured directly: 16.41 GB host and 45.19 GB device for the VAE, 39.81 GB / 94.44 GB for the DiT. Device 
memory scales essentially linearly with rank count (data parallelism, full model replica per rank); host RAM scales slightly sublinearly.

Maximum memory per process. 8,421 MB host RSS per training rank for VAE finetuning (batch 4), rising to 14,228 MB for a DiT rank. On the device: 
23,136 MB per VAE rank and 48,662 MB per DiT rank. The DiT figure was reserved on a 48 GB card, so it is an upper bound rather than a proven floor -- 
the irreducible part is ~31 GB of fp32 weights + gradients + AdamW moments for the 1.9B transformer, so a 40 GB-class GPU is the practical minimum and
48 GB is what has actually been exercised. Dataloader workers add a few hundred MB each.

Total data transferred to/from. 90 GB inbound once at project setup (82.00 GB of Euler-MQ HDF5 + 8.23 GB of pretrained LTX-Video weights), then only 
incremental git pulls. 25 GB outbound over the campaign: the launchers mirror back diagnostics only (`rsync --exclude=checkpoints/`), so weights leave
the site only for the handful of runs promoted to a reference baseline. Resident on project storage: 408 GB (20 runs' checkpoints dominate; a 256x256 
dataset copy would add ~328 GB).

Frequency and size of data output/input. Input: the full 82.00 GB dataset is streamed once per epoch (17.16 MB compressed per simulation, 25.25 MB 
decompressed), i.e. ~82 GB/epoch and 2.40 TB over a 30-epoch run. Output: a 13.94 GB checkpoint (weights + optimizer state) every 1 epoch(s) into a 
fixed set of slots, plus 12 PNG panels of ~448.47 kB and one metrics-CSV append per epoch. The DiT stage writes a 7.17 GB checkpoint every 60 steps 
(166 writes, 1.16 TB of traffic) while reading a 261.63 MB latent corpus that stays in page cache. I/O is bursty, not continuous: checkpoint writes 
are the only large events.

Files and sizes in a typical production run. One VAE run leaves 368 files / 18.74 GB: 2 checkpoints of 4.65 GB each, one 9.29 GB optimizer-state file,
360 PNGs of ~448.47 kB, and a handful of small CSV/YAML/log files. Preprocessing adds 9,000 small `.pt` files (57.77 kB and 1.77 kB) totalling 261.63 
MB -- the only large *file count* in the project. The DiT run keeps a rolling window of 5 x 7.17 GB. Whole campaign (20 VAE runs + 1 DiT run): ~16,376
files, 410.90 GB.

Same answers at higher resolution. Process counts, file counts and checkpoint sizes are unchanged -- the trainable parameter count is fixed by the 
architecture, not the input resolution, so Q1 and Q6's file inventory carry over verbatim. What scales is data volume (with pixel count) and device 
memory (not linearly). 256x256: dataset 319.95 GB (3.9x), so ~320 GB/epoch and 9.37 TB per 30-epoch run; latents grow to 231.07 kB each (1,015.45 MB 
corpus); per-rank device 30.48 GB live at batch 4. 512x512: dataset 1.23 TB (15.4x), so ~1259 GB/epoch and 36.89 TB per 30-epoch run; latents grow to 
924.28 kB each (3.97 GB corpus); per-rank device 29.69 GB live at batch 1, and batch 4 OOMs on a 48 GB card. Host RAM is essentially flat across all 
three.
