# Compute-resource profile

Figures for the compute-allocation proposal, generated by
[`scripts/resource_profile.py`](../scripts/resource_profile.py).

- **`RESULTS.md` -- start here.** The six answers plus the 256/512
  extrapolation, written for lifting into the proposal.
- `report.txt` -- the rendered tool output (dataset inventory, per-question
  tables, resolution scaling, and a condensed "Answers" block at the end).
- `profile.json` -- the same content machine-readable, including the raw
  memory samples, so a number can be traced back to what produced it.

## How these were produced

Generated 2026-08-26 on `lundquist` (2x RTX A6000, 48 GB) against
`euler_mq_dataset/128x128_ds/train.h5`:

```bash
python scripts/resource_profile.py --probe all \
    --probe-processes 2 --probe-batch-sizes 1,4 \
    --resolutions 128,256,512 --resolution-sims 2 \
    --workdir <volume with 40 GB+ free> \
    --json resource_profile/profile.json > resource_profile/report.txt
```

`report.txt`/`profile.json` here were generated just before one labelling fix
(Q5's "read per epoch" now uses file bytes, 82.0 GB, matching the resolution
table, rather than the sum of per-dataset compressed payloads, 75.4 GB). The
numbers are the same data on two bases; `RESULTS.md` uses the file-bytes basis
throughout. A re-run picks up the fix.

`--probe all` runs the real `VaeTrainer`, `preprocess_dataset.py` and the real
DiT trainer for a few steps each under a process-tree memory sampler -- only
the sample *count* is reduced, never resolution, batch size, precision, or the
unfreeze scope, since those are what set the footprint. The VAE probe's own
checkpoint feeds the latent probe, which feeds the DiT probe, so checkpoint and
latent sizes here are measured artifacts rather than derived numbers.

The `--workdir` needs ~40 GB: the probe writes a real ~15 GB VAE
weights+optimizer-state pair per batch-size arm and a real ~7 GB DiT
checkpoint. Do not point it at a quota'd `$HOME`.

## Caveats attached to specific numbers

- **DiT device memory (48.7 GB/rank)** was *reserved* on a 48 GB card, so it is
  an upper bound, not a proven floor. The irreducible part is ~31 GB of fp32
  weights + gradients + AdamW moments for the 1.9B transformer.
- **256/512 memory is measured against synthetic upsampled data** of
  identical tensor shape, since only `128x128_ds` is on local disk. Real
  per-resolution dataset sizes come from the HuggingFace repo tree.
- **`batch_size=4` OOMs at 512x512** on a 48 GB card (confirmed, CUDA short by
  1.57 GiB). 512 needs `batch_size=1` or 80 GB-class GPUs.
- **The DiT stage was only measured at 128x128 latents** (224 tokens). At
  256/512 the sequence grows 4x/16x, which will raise DiT activation memory --
  not yet measured, and the DiT rank already sits at 45 GB live on a 48 GB
  card.
- Multi-node figures are extrapolated. The one 2-node attempt in this project
  (job 521396) hung in rendezvous -- see `infra.md`.
